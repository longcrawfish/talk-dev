# song gift POC 验证清单

> POC 的目的不是"跑通 demo"，而是**提前把可能推翻整个商业模式的风险点逼出来**。每一项都要有明确的可量化验收线，不能凭感觉。三个 POC 跑完，任一项不过都要停下来决策（换路线 / 改规格 / 换技术栈），不能带病推进。

---

## 0. 执行顺序与依赖关系

```
1. 音乐生成 POC（1~2 周）
   ├─ 不通过 → 整个项目要么换路线要么降级（仅歌词+固定音乐）
   └─ 通过 ↓
2. Unit economics POC（2~3 天，但依赖 1 的真实成本数据）
   ├─ 不通过（亏损）→ 调积分模型/赠送策略，重算
   └─ 通过 ↓
3. Next.js on Workers POC（1 周，可与 1 并行，互不依赖）
   ├─ 不通过 → 评估换部署方案
   └─ 通过 → 正式开发
```

- **1 和 3 可以并行**：一个验商业模式，一个验技术栈，互不依赖。
- **2 必须等 1 出数据**：单位经济性测算的输入依赖音乐生成的真实成本与方差数据。

---

## 一、音乐生成 POC（最高优先级，决定 AI 线生死）

### 1.1 候选模型清单

不要只测一个，要平行测，因为可用性、商业授权、成本差异巨大。

| 候选 | 类型 | 关键验证点 |
|---|---|---|
| **Suno 官方 API** | 专门歌曲生成 | 是否开放商用 API、单次成本、是否允许二次分发到 R2 |
| **Udio** | 专门歌曲生成 | 商用 API 是否开放（目前不稳定，作为备选观察） |
| Replicate - MusicGen | 开源托管 | 多为**纯音乐或弱人声**，质量天花板可能不够 |
| Replicate - Stable Audio | 开源托管 | 同上，需实测带词能力 |
| 其它（ElevenLabs Music、MMAudio 等） | — | 作为兜底 |

**第一关就要砍的判断**：Replicate 上很多模型本质是"音乐 BGM 生成器"，不是"歌曲生成器"。如果实测发现 Replicate 路线产不出合格的"带词人声歌曲"，就直接走 Suno API 路线，不要在 Replicate 上耗时间。

### 1.2 能力矩阵验证（硬指标，逐项过）

每项用一个**固定的测试集**（建议 5 个场景 × 中英 2 种语言 = 10 条 prompt，所有模型跑同一套，保证可比）：

| 维度 | 验证内容 | 验收线 |
|---|---|---|
| 带词人声 | 能否生成包含歌词的人声演唱，而非纯伴奏 | 10 条里至少 8 条有人声且歌词基本可辨 |
| 个性化嵌入 | 能否把接收者名字/关键词自然唱进歌词 | 名字出现在至少 6 条，且发音可懂 |
| 多语言 | 英/法/西至少能稳定生成 | 至少英文稳定，法/西作为加分项 |
| 声音性别 | 男声/女声/系统选是否可控 | 性别可控准确率 ≥ 80% |
| 时长 | 单次生成 ≥ 2 分钟（原方案要求） | p50 时长 ≥ 120s |
| 风格覆盖 | 计划支持的 music style 能否产出 | 至少 5 种主流风格可用 |

**任何一项不达标，要停下来判断是换模型还是改产品规格**（比如把"≥2 分钟"改成"60–90s"），不要带病推进。

### 1.3 质量方差测试（最关键、最易被忽略的一项）

**核心逻辑**：礼物是一次性消费，用户不会接受"这次生成的质量明显比上次差"。所以**方差比均值更重要**。

方法：**同一条输入，连续生成 N=10 次**，对输出做盲评打分。

打分维度（建议 1–5 分，定义要写到评分表里，避免主观漂移）：
- 人声自然度（有没有电音/机械感）
- 歌词清晰度
- 节奏/旋律可听性
- 个性化命中（名字/故事是否贴合）
- 整体可送礼度（"我会不会好意思把这个送给朋友"）

**验收线**：
- 标准差 σ ≤ 1.0（稳定性）
- "可送礼度" ≥ 3 分的占比 ≥ 60%（即至少 6/10 是能拿得出手的）
- **没有任何一条出现"灾难性输出"**（刺耳噪音、歌词完全乱、明显抄袭既有歌曲旋律——后者还有版权风险）

如果 σ 很大，说明这个模型不能用于礼物产品，因为**你无法保证用户付钱拿到的那一条不是最差的那一条**。这个结论比"平均分还不错"重要得多。

### 1.4 成本与延迟验证

| 指标 | 测法 | 用途 |
|---|---|---|
| 单次 API 成本 | 直接记录账单 | unit economics 基准 |
| 延迟 p50/p95/p99 | 记录提交到拿到音频的墙钟时间 | 决定要不要做异步 + 邮件通知、以及给用户的等待承诺 |
| 失败率 | 跑 100 次统计 5xx/超时/无音频 | 决定重试策略与重生成系数 |
| 限流/配额 | 压测或读文档 | 决定并发上限、是否要做排队 |

### 1.5 法律条款（必须逐条确认，不通过则该模型不可用）

- 生成内容**版权归属**（归用户？归平台？归模型方？）
- 是否**允许商用**
- 是否**允许下载、二次分发到你的 R2、再向第三方播放**
- 这条直接决定能否合法做"收礼页下载"和"付费解锁"。如果某模型不允许分发，无论质量多好都不能用。

## 二、Next.js on Workers 兼容性 POC（决定技术栈是否成立）

这块失败概率比想象中高，建议**在写任何业务代码前**先跑一个最小骨架。

### 验证清单（每一项做一个最小 demo，过则勾，不过则评估替代方案）

1. `@opennextjs/cloudflare` 能否正常构建 + 部署当前 Next.js 版本（注意锁版本，Next 大版本升级常踩坑）。
2. **Google OAuth**：用 Auth.js（NextAuth）走 Google，能否完成登录、Session 持久化、回调。重点测 callback URL 在 Workers 域名下是否正常。
3. **Creem 支付回调**：webhook 能否被 Workers 接收、签名校验能否通过、回调里能否访问 D1。
4. **D1 binding**：读写、事务（积分扣减必须有事务）、并发写压测（SQLite 单写者，关注 `SQLITE_BUSY`）。
5. **R2 binding**：上传、Range 请求（音频流播必需）、presigned URL（如果需要前端直传封面图）。
6. **Workers Queues**：生产者投递、消费者执行、消费者执行时长上限（音乐生成耗时任务的关键限制）、失败重试与死信。
7. **Node API 兼容性**：项目里若用了 `crypto`、`fs`、`Buffer` 等非 Edge 原生 API，逐一验证。
8. **Cron / 定时任务**：积分过期清理、草稿 24h 清理需要 Cron Trigger，验证能否稳定触发。

**验收线**：1–6 全部通过才进入正式开发；7、8 有任一项不通过，要立刻定替代方案（比如用 Cloudflare Pages + Functions 分离，或某些任务放到外部小服务）。

## 三、Unit economics 测算 POC（决定赠送额度会不会亏）

不是跑代码，而是**建一张表**。关键是要把"隐性成本"和"概率性成本"显式列出来。

### 3.1 Unit economics 表结构（每生成一首歌）

| 项目 | 数值 | 说明 |
|---|---|---|
| API 调用成本 | ? | 单次音乐生成（注意：一次成功背后可能有失败重试） |
| **重生成系数** | ? | **平均生成几次才出一条用户买单的**——用 1.3 方差测试数据反推，比如可送礼度 ≥3 占比 60%，则系数 ≈ 1/0.6 ≈ 1.67 |
| 歌词生成成本 | ? | OpenRouter 调用 |
| 封面生成成本 | ? | Replicate 图片 |
| R2 存储 | ? | 按音频大小 × 月数 |
| D1 读写 | ? | 一般可忽略，但草稿高频写要估 |
| 邮件通知 | ? | 每次生成至少 1 封 |
| 流量/带宽 | ? | R2 出口免费，但要确认；Workers 请求量计费要估 |
| **单首交付总成本** | Σ | 定价基准 |

### 3.2 敏感性分析

回答两个问题：

1. **积分定价**：一首歌定 X 积分，每个积分隐含多少成本？用户花多少钱买一首歌？要**毛利 > 0 且有 buffer**。
2. **赠送额度安全线**：假设前 1000 个新用户每人赠 3n 积分、转化率 r%、其中薅羊毛比例 c%，**最坏情况下站点要倒贴多少钱**？这个数字必须在你可承受范围内。

**验收线**：
- 单首交付成本 ÷ 用户实付单价 ≤ 0.7（留 30% 毛利 buffer 给支付手续费、退费、客服成本）
- 赠送额度的最坏情况亏损额 < 你愿意为冷启动投入的预算

如果算下来发现"送 3n 就亏"，那就要么降 n、要么提高积分门槛（比如解锁才扣、而非生成即扣），**结论要能反过来影响产品设计**，而不是先做产品再算账。

## 四、强制产出物（POC 跑完必须交付）

三个 POC 跑完，除了"行/不行"的结论，建议**强制产出两份文档**：

1. **《模型选型与质量基线报告》**：记录每个模型的方差测试数据、验收线达成情况、最终选型理由。以后质量翻车或要换模型时有据可查。
2. **《Unit economics 基准表 v1》**：作为后续所有积分定价、促销活动的约束边界。赠送活动上线前都要回这张表算一遍"会不会击穿成本"。

---

## 五、降级 / 止损预案

如果 POC 发现 AI 音乐质量不达标，需要预先想清楚：

- free-gift-maker 是否能独立成立？
- 是否有降级方案（如仅歌词朗诵 + 固定音乐）？
- 避免 all-in 在 AI 音乐质量上。

POC 阶段就要把"不通过"的应对路径列出来，而不是等结论出来再慌。
