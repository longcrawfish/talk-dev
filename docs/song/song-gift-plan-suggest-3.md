# song gift 规划建议（第 3 轮）

> 针对 `docs/song/song-gift-plan.md` 的评审建议。同时参考了 `song-gift-plan-suggest-1.md`（AI-1，偏产品/SEO/商业策略）与 `song-gift-plan-suggest-2.md`（AI-2，偏工程/成本/风控）。两份建议高度互补，本文只讲**还缺或值得商榷**的地方，已达成共识的不再重复。

---

## 总体评价

原方案方向正确（免费引流 → AI 商业化 → 收礼页裂变），两份 AI 建议各有侧重：

- **AI-1**：偏产品 / SEO / 商业策略，乐观、偏高层。
- **AI-2**：偏工程 / 成本 / 风控，务实、抓关键缺口。

两者高度互补。下面只讲被低估或值得商榷的点，以及两份建议分歧处我的倾向。

---

## 一、两份建议都触及但没点透的最大风险

### AI 音乐质量对"礼物"场景是致命的，不只是 POC 通过与否

- 通用 AI 工具（Suno 类）用户能容忍质量方差，但**礼物是一次性、高情感投入、收礼人当场打开**，质量翻车 = 创作者和收礼人同时失望，且无法重来。
- AI-2 把"模型选型 POC"列为第一优先是对的，但更深一层：即便 POC 通过，**生产环境的稳定性、一致性**（同样输入第二次质量崩了）才是礼物产品真正的门槛。
- 建议 POC 里加入「同输入多次生成的方差测试」，而不仅是「能不能生成带词人声」。（详见 `poc-checklist.md`）
- 建议：上线初期在收礼页 / 分享页做**期望值管理**（"AI 个性化创作"而不是"专业定制"），否则容易引发客诉和差评反噬 SEO。

---

## 二、被两份建议低估的点

### 1. 场景页是"瘦页面"陷阱

三份文档都列了一堆场景（Birthday / Anniversary...），但这些页如果只是套模板的薄内容，Google 不会给排名。AI-1 提了 URL 结构，但没强调**每个场景页要有独立的真实文案、真实示例音频、真实礼物案例**。否则做了等于没做，甚至被判 Doorway Pages 反伤。建议 MVP 先做 1~2 个场景深度页，跑通再扩。

### 2. pixabay 音乐的授权与归属

原方案说"采集可商用音乐"，但 pixabay 的音乐授权条款、是否允许二次分发到 R2、是否需要署名，需要**逐首核实并留存凭证**。免费工具一旦被版权方投诉下架，等于免费入口直接断掉。

### 3. 礼物链接的生命周期与存储成本

三份文档都没说 `/gift/[id]` 的链接是永久有效还是定期失效。礼物有"多年后回看"的情感诉求，但永久存储意味着 R2 + D1 成本持续累积，且病毒传播后可能被大量打开。建议明确策略：链接永久、但音频冷存储 + 按需取回，或明确 N 年保留期。R2 零出口流量费是优势，但存储费仍要算进 unit economics。

### 4. 收礼页的播放环境

收礼人打开链接多在 IM 内置浏览器（微信 / WhatsApp / iMessage），这些环境对**音频自动播放有严格限制**（需用户手势），且 iOS 锁屏播放、后台播放行为不同。"仪式感"设计要基于这些限制来设计首屏交互，不能按标准浏览器假设。

### 5. 礼物的时间敏感性

生日 / 纪念日是固定日期，异步生成 + 队列 + 邮件通知意味着创作者要提前操作。建议在产品里**显式提示"建议提前 X 小时创作"**，否则临时创作遇上限流 / 排队，礼物错过日期 = 差评。

### 6. 单位经济性不只是成本，还有"重生成摊销"

AI-2 提到重生成概率摊销，这点很关键。建议在 unit economics 表里把**单次成功交付的实际重生成系数**（比如平均生成 2.3 次才出可用结果）作为显式变量，而不是按理论 1 次算。这直接决定赠送额度会不会亏。

## 三、两份建议的分歧，我的倾向

| 分歧点 | AI-1 | AI-2 | 我的倾向 |
|---|---|---|---|
| 工具入口 | 收敛为单一入口（mixed 为主） | 保留三工具 | **折中**：用户侧单一入口（AI-1 对），但**保留独立落地页**做 SEO（三个 URL 抓不同搜索意图），内部是同一组件——这两者不矛盾 |
| 歌词是否先生成 | 合并为一步（先音乐后看词） | 保留歌词前置 | **倾向原方案 / AI-2**：歌词是礼物个性化核心（名字 / 故事），先出词让用户校验再花钱做音乐，是更省成本的校验步骤；但 UI 上歌词只做轻量预览，不要让用户在词上反复纠结 |
| MVP 范围 | 大幅削减（砍 PDF / 上传 / 下载 / 草稿 / 后台） | 基本保留 | **倾向 AI-1**：MVP 只验证核心闭环；但**收礼页的下载功能建议保留**——它是礼物价值感的关键，砍掉会削弱分享动机 |

## 四、建议的最先做的三件事（优先级）

1. **音乐生成 POC + 方差测试**（含成本 / 质量 / 稳定性）—— 决定整个 AI 线能否成立。
2. **Unit economics 表**（含重生成系数）—— 决定积分定价和赠送额度会不会亏。
3. **`/gift/[id]` 的可点击原型验证收礼体验**（含 IM 内置浏览器音频限制）—— 这个页面是整个增长飞轮，值得单独把它打磨到位，比工具页优先级更高。

> POC 的具体验证清单见 `poc-checklist.md`。

---

## 五、一个被完全忽略的点：失败 / 止损预案

做一份"失败 / 止损预案"——如果 POC 发现 AI 音乐质量不达标：

- free-gift-maker 是否能独立成立？
- 是否有降级方案（如仅歌词朗诵 + 固定音乐）？
- 避免 all-in 在 AI 音乐质量上。

POC 阶段就要把"不通过"的应对路径列出来，而不是等结论出来再慌。

---

## 六、总结

- 原方案 80% 正确，方向无需大改。
- 两份 AI 建议分别覆盖了产品和工程两侧，**但共同的最大盲点是：没把"礼物场景对质量方差零容忍"作为产品定义级风险来对待**。
- 关键不是"AI 能不能生成歌"，而是"AI 能不能**稳定**生成**每一首都能拿得出手的**歌"。
- 优先级：POC（音乐 + 成本 + 技术栈）> `/gift/[id]` 体验 > 工具页打磨。
